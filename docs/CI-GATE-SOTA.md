# ci_gate vs SOTA — supply-chain and quality gate comparison

**Status**: ACTIVE
**Type**: reference
**Source**: `scripts/ci_gate.py` at HEAD
**Last Updated**: 2026-09-13

Owner: Architecture · Last updated: 2026-09-10 · Status: **living document**

This is the no-compromise comparison the user asked for: how `scripts/ci_gate.py`
(executed by local n8n via `scripts/ci_bridge.py`) measures against the current
state of the art in CI/CD verification, and exactly what is **missing**.

Read this with:
- `docs/ACCEPTED_RISKS.md` — the register that machine-exempts reviewed findings
- `.github/workflows/ci.yml` — the Actions jobs this gate replaces
- `docs/N8N-SETUP.md` — how n8n invokes the gate

## 1. What "SOTA" means here

The reference frame is the union of five widely-adopted standards, not a single
vendor product:

| Reference | What it demands |
|---|---|
| **SLSA v1.0** (Build track L1–L3) | Provenance exists (L1), is generated by an authenticated/hosted builder (L2), and the build is hardened + non-falsifiable (L3) |
| **NIST SSDF** (SP 800-218) | PW.4 reuse with integrity, PW.7 review/analyse, PW.8 test executables, PS.2 verify release integrity, PS.3 archive provenance, RV.1 identify/confirm vulns |
| **OpenSSF Scorecard** | Pinned dependencies, least-privilege tokens, branch protection, signed releases, SBOM, fuzzing, SAST, dependency-update automation, security policy, CI tests |
| **OWASP ASVS 4.0 / SAMM** | Verification requirements mapped to automated checks; SAMM measurement of the security practice |
| **CycloneDX / NTIA SBOM minimum elements** | Machine-readable inventory: supplier, component, version, unique IDs, dependency relationships |

## 4. The nine gaps, stated plainly

These are **not** implemented. They are listed here rather than hidden behind a
green tick, per the project's honesty rule (see `docs/ACCEPTED_RISKS.md`).

1. **DAST / running-app testing** — no ZAP or equivalent against a live instance.
2. **Fuzzing** — no property-based/coverage-guided fuzzing (e.g. Atheris) in the gate.
3. **VEX** — no exploitability statements attached to the SBOM.
4. **Transparency log** — cosign runs with a local key and no Rekor entry, so the
   signature is verifiable but not publicly witnessable. Keyless OIDC signing is
   impossible without a hosted CI identity.
5. **Reproducible inputs** — `requirements.txt` is frozen but not hash-pinned;
   `pip install --require-hashes` is not enforced.
6. **Signed commits / DCO** — commit *format* is enforced; authorship provenance is not.
7. **Depth of SAST** — semgrep is not a substitute for CodeQL's dataflow analysis.
8. **Container image scanning** — the image is optionally built but not scanned as
   an artifact, nor pushed/signed to a registry.
9. **Enforcement** — the local gate can block *n8n*, but GitHub cannot be told to
   refuse a merge on a private free-tier repo (branch protection is 403). PRs stay
   mergeable by design; the gate is advisory-at-the-merge-button.

## 5. How exemptions work (so the gate can never be gamed silently)

`gate_trivy_fs`, `gate_osv` and `gate_licenses` read `docs/ACCEPTED_RISKS.md`
and exempt findings whose **vulnerability ID** (CVE-*/PYSEC-*/GHSA-*) or
**package name** appears on a row marked Accepted / Deferred / Needs decision.

Consequences, by design:
- A reviewed risk (e.g. `chromadb` CVEs, RISK-001) does not turn every PR red.
- The exemption is *visible*: acknowledged findings are printed under the failure
  block, never mixed into the pass count.
- Deleting or resolving the risk row **re-surfaces the finding** on the next run —
  the register and the gate cannot drift apart.
- An unresolved licence call (RISK-002 `pymupdf`, AGPL) is surfaced as acknowledged,
  not silently allowed.

## 6. Operating the gate

```bash
scripts/ci_gate.py --sha <commit>                 # human summary
scripts/ci_gate.py --sha <commit> --json          # machine JSON
scripts/ci_gate.py --sha <commit> --with-coverage --with-docker --with-mutation
scripts/ci_gate.py --init-signing                 # one-time cosign keypair
```

Heavy gates are opt-in because the gate is polled by n8n every 30 minutes:
`--with-docker` (cold image build), `--with-mutation` (mutmut runs the suite per
mutant), `--with-coverage` (instrumented run). The blocking set stays fast.

Scan tools live in an isolated venv (`~/.local/share/jarvis-ci-tools/venv`) plus
`~/.local/bin`, so the project's pinned `.venv` is never polluted by their
dependency trees.

  at the top of each workflow file.

  merge-tree --write-tree` + `commit-tree`), matching GitHub's `pull_request`
  checkout semantics instead of gating the raw head. Stale Dependabot branches
  previously failed forever against a fixed `main`; now they are judged on the
  code that would actually land. Merge conflicts are reported separately.

  publish model: `workflow_entity.activeVersionId` was NULL) and the systemd unit
  pointed `N8N_USER_FOLDER` one level too deep, so the service was reading a
  different, empty database. Both fixed; JARVIS-CI-Local now polls every 30 min.
